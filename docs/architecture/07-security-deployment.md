# Security and deployment

## Authentication and authorization

- Use invited local accounts initially, with ASP.NET Core Identity for password hashing, account lifecycle and cookies. Back the needed Identity stores with Dapper using the same MySQL database. Implement the stores needed by the approved flows and test their lockout, revocation and credential-change behavior. Start with an operator-managed account setup and documented recovery, and consider external OIDC if account management becomes onerous. Use MFA for Internet-exposed operator and admin accounts. [Microsoft guidance on custom Identity stores](https://learn.microsoft.com/en-us/aspnet/core/security/authentication/identity-custom-storage-providers?view=aspnetcore-10.0)
- Use same-origin `Secure` and `HttpOnly` cookies with a suitable `SameSite` policy, an anti-forgery token for unsafe requests, exact trusted proxy configuration and HTTPS. Verify WebSocket origins and subscription membership, and keep sessions bounded and revocable. Enforce access on every property read and mutation. When membership changes, remove or disconnect affected SignalR subscriptions and require a fresh authorized join.
- **Viewer** can read property state and permitted history. **Operator** can also submit allowed device commands and manual overrides. **Admin** can manage members, devices, provider connections and rule activation. Keep membership checks server-side and apply scoped SQL predicates. Frontend gating improves usability and carries no access authority.
- Validate command types, targets, limits, expiry and idempotency before queuing and again before dispatch as appropriate. Audit user and service actions, rule/version and decision reasons, state transitions, and provider outcome references. Restrict audit access and redact credentials, callback query parameters, tokens and provider payloads from logs and error responses.

## Secret storage

Provider secrets, user OAuth refresh tokens, MySQL passwords, and encryption keys live on the backend. Use a cloud secret store or restricted file-mounted Docker Compose secrets for static values. Store rotating OAuth tokens encrypted in a dedicated backend vault or as encrypted database records with keys kept separately. Coordinate refresh and persist replacement tokens atomically. Use versioned key material for rotation and recovery. Persist the ASP.NET Core Data Protection key ring on a protected volume or supported cloud store, with explicit encryption at rest for the key ring. Keep it stable across redeploys. Development uses local secret storage and synthetic provider accounts or fixtures. [Docker Compose secrets](https://docs.docker.com/compose/how-tos/use-secrets/) · [ASP.NET Core Data Protection configuration](https://learn.microsoft.com/en-us/aspnet/core/security/data-protection/configuration/overview?view=aspnetcore-10.0)

Use provider-hosted consent for eWeLink and portal linking plus server-side vault provisioning for the Tuya project. Keep app secrets, Tuya access secrets, OAuth tokens, gateway tokens and local keys out of frontend state and responses. Local device credentials remain with the agent where feasible. Return safe authorization, sync and revocation status in the UI. On unlink or revocation, disable the affected binding, invalidate its cached credentials and recheck dependent control eligibility. Record redacted connection and policy changes.

## Remotely switched electrical loads

- Classify each switched endpoint during commissioning, including whether it controls a water heater or another safety-critical load. Disable remote control by default. Require property Operator or Admin permission and a per-endpoint allowlist. Admins approve or revoke manual remote and unattended control independently. Audit policy changes, manual overrides, automatic decisions, chosen routes and command outcomes.
- Verify the installed relay/contactor and appliance suitability and ratings for the actual load and circuit with the installer. Preserve the appliance thermostat, independent thermal cutoff, circuit protection, BMS safeguards and physical manual controls. Keep protection settings outside the exposed command catalog. Network OFF requests and relay feedback provide operational control and status. Physical isolation and hardware protections remain the safety path.
- Before allowing unattended water heating, verify a site-local independent runtime limit and the behavior during WAN loss, device reboot and power restoration. Require documented site handling for unexpected energization, stuck output or unreachable control. Use application runtime deadlines, approved operating windows, minimum switch intervals, command deduplication, independent manual lockout and reconciliation to reduce operational risk. A manual override cannot lift a hard limit. [Water heating execution policy](06-automation-engine.md)

## Container topology

| Component | Deployment behavior |
| --- | --- |
| Reverse proxy | Public TLS termination where required. Forward REST, OAuth callbacks and SignalR with WebSocket support. Serve the built SPA on the same origin via the proxy or API static assets. Route `/api` and the hub before the SPA fallback. |
| Application | One continuously running .NET container with API and hosted services. Use a restart policy, non-root runtime, graceful termination window, and stop-first updates to avoid overlapping dispatchers. |
| MySQL | MySQL 8.4 LTS on a private network and persistent storage, or a compatible managed MySQL 8.4 service for cloud. Use separate runtime, migration and backup credentials. Do not expose the DB port publicly. |
| Migration job | Run once per release before application startup with DDL credentials. Refuse startup when the schema is incompatible. |

Cloud deployment places the application on an always-on host with outbound provider access, an HTTPS endpoint and durable database storage. It stays available when the property loses power, though property telemetry or devices may stop responding. Self-hosting uses the same Compose topology on a protected host and can restrict UI access to a LAN or VPN. Validate OAuth callback routing, HTTPS and provider egress for the chosen exposure. On-prem hosting keeps access to stored or local data over the LAN when WAN access fails, subject to site power and network availability. It does not sustain cloud control during the outage. Consider UPS power and local link availability wherever offline requirements justify it.

Keep IoT devices, local gateways and MQTT brokers off the public Internet. Place them on an isolated network where feasible and limit traffic to the approved local agent or controller and required vendor egress. An agent enrolls for one property with a revocable per-agent identity and initiates TLS connections to the backend. Validate property and binding authorization on every import. Restrict broker accounts and topics to the required devices, protect local credentials at rest, and allow only approved local discovery or configured hosts. The first agent receives no actuation authority. [Local integration design](05-integrations.md)

## Operations, backup and recovery

- Separate liveness from readiness. Liveness checks the host loop. Readiness checks schema and MySQL access. Per-integration status reports last contact, observation age, throttle state and credential issues instead of making every provider outage fail readiness. Limit details on anonymous health endpoints.
- Use structured logs with correlation IDs and credential redaction. Track poll and event-stream health, observation age, quota burn, queue depth/oldest work, unknown commands, overdue load deadlines, suppressed actions, rollup lag, database growth and last successful backup. Avoid high-cardinality labels for telemetry and keep audit records separate from diagnostics.
- Take encrypted scheduled MySQL backups and retain copies off-host, with separately protected recovery material for tokens and sessions. Proposed initial objectives are a 24-hour RPO and a 4-hour RTO, pending operator agreement. Test restore into an isolated environment using the matched schema and keys. Start with live dispatch paused, reconcile commands and provider sessions from fresh observations, and explicitly re-enable controls. A restored database may omit operations delivered after the backup, so do not automatically replay its queue. Document rollback, key recovery, emergency pause and manual control procedures.
