# Integrations

Provider research below uses public documentation. Validate field availability, entitlements, region and installed hardware before enabling a binding. Use the verified provider contract from onboarding for request details.

## Growatt Cloud and local options

See [Milestone 2 Growatt access research and normalized integration](../integrations/growatt.md) for the implementation boundary and account prerequisites.

Its product materials identify the SPF family as parallel-capable and supported by remote monitoring. Its installer manual documents token-backed data access in installer workflows. None of that establishes this ShinePhone account's eligibility or which SPF 5000 ES fields an authorized API exposes. | Supported cloud push or approved partner data feed | Growatt describes vendor-operated MQTT forwarding as an option. ### Installation mapping and validation

- Store master and slave readings by inverter and source and attach both devices to one installation. Record AC input/grid signal, PV and load power/energy, battery voltage, SOC and signed charge/discharge power, operating mode, warnings and faults as distinct metric types where supported. Label unsupported and uncovered metrics visibly. Document the field, units, sign, subject, cadence, provenance and any quality limitations for each verified mapping.
- Prefer an independently validated site total when present. Sum only contemporaneous, non-overlapping per-inverter PV, load, or battery power flows that the telemetry contract or commissioning proves additive. Shared battery volts and SOC represent a single battery and need one authoritative source. Never sum mirrored site counters or infer household consumption from inverter outputs unless the measurement boundary covers the household. Use a completeness flag and explicit missing-member list when a total is partial. Avoid switching between counters without reestablishing a baseline.
- Distinguish observed grid input from inverter mode, Internet reachability and import power. Gate control that depends on grid state until a trusted measurement works through a real loss and recovery. Verify the BMS model, protocol and commissioned limits with the installer. Growatt's published manual lists a 400 Ah recommendation for two parallel units, compared with this site's reported 200 Ah battery. Have the installer reconcile the exact hardware revision, BMS current limits and approved operating envelope before changing load automatically. Inverter settings and BMS protections stay outside the write scope. [Growatt SPF 3500–5000 ES manual, parallel installation](https://de.growatt.com/upload/file/SPF_3500-5000_ES_Benutzerhandbuch_DE_202109.pdf)

## Daikin ONECTA

Daikin's public developer guidance confirms official monitoring and control, self-service private developer credentials, terms acceptance and EMEA availability. Its FAQ publishes a default 200 calls/day for private developers and sliding-window accounting. The public information does not establish the exact model capabilities, request costs, token rotation behavior, or support for a 10 °C heating setpoint on the installed units. Consult the portal contract with the registered app before implementation. [Daikin developer FAQ](https://www.daikin.ie/en_gb/product-group/control-systems/daikin-developer-portal.html) · [ONECTA Developer Portal](https://developer.cloud.daikineurope.com/)

- Register the app and its exact HTTPS callback. Use server-side OAuth2 authorization code with protected, expiring state tied to the initiating property admin and PKCE subject to the provider contract. Obtain documented scopes and consent. Refresh ahead of expiry using one in-flight refresh per credential, persist replacements atomically, and signal reauthorization on revocation or unrecoverable refresh failure. Store all credentials and tokens behind a server-side vault. [OAuth 2.0 security guidance](https://www.rfc-editor.org/rfc/rfc9700)
- Discover and map devices on demand. Read each model's current/target temperatures, power and mode when supported. Derive separate read/write capabilities and numeric min/max, step, and mode applicability. Enable power, mode, or setpoint writes only when exposed and validated for that unit. Reject unsupported targets without silent coercion or mode changes.
- Share an outbound budget by provider-account quota scope across pollers, discovery, status reads, retries, and commands. Confirm whether token calls have a separate quota. As an initial budget example, one billable account request every 10 minutes uses 144 of 200 calls/day and leaves 56 for other calls. Use this cadence only if account-wide retrieval fits one request and a measured margin remains. Slow polling if per-device calls are required. Reserve capacity for admitted commands and readback and coalesce sample refreshes. UI-driven reads use the database cache.
- Acknowledgements and readback are separate. Verify on supported fresh provider/device readback after a bounded delay, reusing scheduled polling where possible. Distinguish accepted/unverified, rejected, confirmed and unknown outcomes. Confirm device availability, update latency, setpoint limits and app consent during supervised commissioning.
- Keep ONECTA as the official HVAC baseline. Evaluate a separate local adapter only against an exact controller and supported contract. Home Assistant documents a model-specific local integration that can inform a future feasibility check. The current design needs no Daikin MQTT path or vendor SDK. [Local controller compatibility in Home Assistant](https://www.home-assistant.io/integrations/daikin/)

## Smart Life and Tuya

Smart Life is the app and account for this site's devices. Tuya Cloud is the developer integration. Use a Smart Home cloud project in a data center serving the app account's region. Subscribe and authorize the required IoT Core services and link the Smart Life account through Tuya's documented authorization flow. The backend uses project access credentials, HMAC-SHA256 request signing and Tuya project access tokens. Tuya's account-linking and signing flow is distinct from CoolKit's app OAuth flow. Verify API service coverage, plan limits, renewal and regional scope for the actual project. ## Adapter contracts and failure policy

| Application port | Contract |
| --- | --- |
| Discovery | Returns external identities and available capabilities without changing the property inventory. |
| Observation read and optional subscription | Return timestamped binding and endpoint identities, normalized readings, source sequence or event identity, quality and per-target outcomes. Polling, vendor push and local imports use the same ingestion path. |
| Command sender | Accepts a typed target, one selected binding, correlation ID and stable idempotency key where supported. Returns structured acceptance, rejection or unknown outcome. Omit this port for read-only sources. |
| Command verifier | Obtains authoritative status or fresh reported state and exposes when verification is unsupported. |

Use typed `HttpClient` through `IHttpClientFactory`. Apply limits at the actual account, app, IP, project or API scope and reserve capacity for verification. Treat schema violations, invalid authorization, throttling, transport failure and explicit device faults as different outcomes. Honor `Retry-After` when available and apply budgeted capped exponential backoff with jitter to eligible reads. Reconnect push streams with bounded backoff and reconcile gaps within budget. A token-related `401` may trigger one coordinated refresh and one safe read replay. Repeat writes only under documented idempotency or proof they were never transmitted. Persist and reconcile ambiguous writes across routes. Preserve provider correlation IDs without payloads or tokens in logs.

## Future local agent

An optional property agent discovers approved devices on its LAN, accepts explicit configuration where discovery is unavailable, and reports candidate identities for admin confirmation. Use only documented gateway, LAN, Matter or MQTT interfaces appropriate to the installed hardware. The agent initiates authenticated outbound communication. It buffers a bounded set of timestamped observations with source IDs and sequences and resumes synchronization idempotently. Retained MQTT messages and delayed events are historical unless their source timestamp and quality meet live freshness rules. While disconnected, the central backend cannot see newly buffered samples. Site power, LAN and supported device behavior determine local visibility.

Link local and cloud bindings to the same physical device and channel after identity verification. Select a primary and eligible fallback per metric, mark disagreement and prevent double-counting. The first agent is read-only and optional. If a later phase adds writes, keep one owner per physical device and route through the existing ledger with intent IDs, expiry and durable acknowledgement/deduplication. Require an explicit ownership transfer protocol and actuator support for independent offline dispatch, including after contact loss.
