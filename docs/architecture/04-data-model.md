# Data model

Use MySQL 8.4 LTS with InnoDB, Dapper and MySqlConnector. Group SQL by use case and use parameterized queries and explicit transactions. Use `BIGINT UNSIGNED` for internal identity keys, bounded `VARCHAR` for stable codes, and `DATETIME(6)` for UTC instants. Normalize UTC at the application boundary and set database sessions to UTC. Store a property's IANA timezone separately. Use JSON for validated rule definitions, provider-specific configuration and capability constraints. Keep relationships and routinely filtered fields in columns. See [ADR 0003](adr/0003-mysql-dapper.md).

## Entities and keys

| Entity | Key columns and relationships |
| --- | --- |
| `properties`, `users`, `property_memberships` | Property name and `time_zone_id`; app user ID and identity fields; membership keyed by `(property_id, user_id)` with Viewer, Operator or Admin role. Index `(user_id, property_id)` for navigation. |
| `property_rooms`, `installations`, `devices`, `installation_devices` | Property-owned rooms, installations and physical devices. Devices have optional room, friendly name, type, optional manufacturer/model, monitoring flag and version. Installation membership records identify roles such as master, slave or shared battery. Index `(property_id, room_id, type_code, id)` for inventory views. |
| `device_endpoints`, `device_capabilities` | Each device has a stable default endpoint and optional named channels. Unique `(device_id, endpoint_key)`. Capabilities keyed by `(device_endpoint_id, capability_code)` carry support state, readable/writable flags, optional unit/range/step/modes, and mapping version. Store operator control enablement separately from what a provider can do. |
| `integration_connections`, `provider_bindings`, `provider_endpoint_bindings` | Connection type, property, provider budget/account key, region, credential reference and health. Bind a case-sensitive external identity unique within `(connection_id, external_kind, external_id)` to a device or installation. Endpoint bindings map external channel selectors to stable device endpoints under that binding. Keep per-binding communication and synchronization state. Persist provider enablement and capability mapping; secret material stays in the vault. |
| `telemetry_subjects`, `measurement_definitions`, `telemetry_series` | A subject points to exactly one device endpoint or installation. Definitions declare canonical metric code, value kind, unit and behavior such as gauge, counter, interval delta, state or event. Each unique `(subject_id, metric_code, source_key)` is one series. The source identifies an endpoint or installation binding or a versioned derivation. Source policy selects eligible series per subject and metric. |
| `telemetry_samples`, `latest_readings` | History key `(series_id, observed_at_utc, sample_id)`. Keep source sample ID or deterministic fingerprint, receipt time, quality/reason and typed value (`DOUBLE`, `BOOLEAN`, or bounded status code). Store the latest ordered observation quality and last valid value per series, each with its own timestamps, plus the freshness limit. Index latest readings through series and subject. |
| `telemetry_rollups_hourly`, `telemetry_rollup_state` | Migration 017. UTC hours keyed `(series_id, bucket_start_utc)` with count, covered seconds, min/max, time-weighted average, value sum, last observation, ON seconds and transitions, measured Wh, estimated ±Wh and quality flags. The state records each series' contiguous materialized range. Local days are calculated from hourly rows and raw partial hours. See [historical telemetry](10-historical-telemetry.md). |
| `logical_devices`, `logical_device_assignments`, `logical_device_audit` | Migration 018 (019 adds `creation` and lifecycle audit actions; see [logical device management](14-logical-device-management.md)). Property-owned logical identities whose channels are assigned to physical devices, optionally one endpoint, for `[valid_from_utc, valid_to_utc)`. One open assignment per channel; overlap is validated under a property row lock. Append-only audit. See [logical devices](11-logical-devices.md). |
| Migration 020 additions | `properties.description`, `creation_request_id` (unique, idempotent creation) and `deleted_at_utc` (soft delete; every membership check excludes deleted properties). `rooms.description`. `devices.display_name` (custom name that sync never overwrites) and `retired_at_utc` (the row of a device moved to another property, kept with its history). `management_audit` records property, room, device assignment, room, name and move events with the other property and device for moves. See [property, room and device management](16-property-room-device-management.md). |
| Migration 021 alerts | `alert_rules` (validated JSON definition, severity, correlation family, timing, notification policy, revision, soft delete), `alert_rule_revisions` (snapshot per change), `alert_rule_state` (persisted detection phase and evidence), `alert_evaluation_locks` (per-property evaluation lock), `alert_incidents` (unique generated `active_key`: one active incident per property and family), `alert_incident_rules`, `alert_incident_events` (timeline with evidence), `notifications`, `notification_recipients` (read state, in-app visibility), `notification_deliveries` (per-channel attempts and outcomes), `notification_preferences`. Additive; no grant change. See [alert rules, incidents and notifications](17-alerts-and-notifications.md). |
| `dashboard_groups`, `dashboard_widgets`, `dashboard_values` | Migration 011 stores ordered property layouts. Migrations 012 and 013 add independent widget width, measurement columns, and per-value color settings. Composite property foreign keys scope the hierarchy. Source keys refer to registered series or assigned provider measurements and survive source removal. The server validates bindings, resolves routes from visible sources, and saves the layout atomically with a revision check. |
| `rule_definitions`, `rule_versions`, `rule_runtime`, `automation_evaluations` | Property, versioned definition JSON, enabled mode and priority; runtime checkpoint with last evaluated event, latch and pending timers; evaluation trigger identity, rule version, input references, outcome and reason. Unique evaluation trigger identity per rule version and execution mode. |
| `measurement_boundaries`, `measurement_boundary_members` | Property-owned versioned definitions for verified whole-house, circuit and appliance coverage. Point to authoritative measurement subjects and explicitly identify non-overlapping contributors for derived totals. Mark overlap or unverified coverage for display. |
| `automation_work`, `manual_overrides`, `device_control_state` | Durable due work keyed by trigger identity with status and deadline; override actor, endpoint or device scope, target, version and expiry or release; desired target/version, pending command pointer and last applied command status per control group. |
| `controlled_load_policies`, `controlled_load_runtime` | Per-endpoint classification, approved remote/manual and unattended permissions, operating window, maximum runtime, minimum on/off times, policy version and commissioning reference. Runtime records earliest possible energization time, deadline, observed state and whether it is uncertain. Keep the active deadline and its due work durable. |
| `device_commands`, `command_attempts`, `audit_events` | Physical device, endpoint, typed action, actor or evaluation, target and version, status, eligibility/expiry and idempotency fingerprint. Unique application request identity scoped to property and producer. Append-only attempts record the chosen binding, mapping version, outcomes and provider references. Audit records identify actor, action, property, resource and redacted changes or reasons. |
| `alert_incidents`, future `notification_deliveries` | Property-owned alert key, evidence, open/clear times and optional acknowledgement. Keep one active incident per deduplication key through a unique active-record constraint. Future deliveries are unique per event and destination and carry attempt and due status. |

Root device, installation, room and connection identities have `(property_id, id)` unique keys. Use composite foreign keys wherever ownership can diverge, such as room assignments, installation membership, provider bindings and command targets. Require endpoint bindings and commands to reference endpoints belonging to their physical device. Child tables reachable through one parent can inherit its scope. Require the property in application access checks and SQL predicates. Index due work on `(status, due_at_utc, id)`, commands on `(device_id, created_at_utc, id)` and audit/history lists on `(property_id, occurred_at_utc, id)` where applicable. Archive devices to preserve operational history and audit links.

## Capability representation

Keep a small application-owned catalog of typed capability codes and allowed operations. Persist a device's capability metadata and endpoint bindings as rows so Dapper queries can filter on them. Use validated JSON only for optional constraints that vary by capability. Keep normalized reported and desired state in the existing projections and use a typed command catalog for writes. [ADR 0007](adr/0007-device-capabilities-and-provider-bindings.md)

| Capability examples | Value and access |
| --- | --- |
| `Switch` | Boolean reported state and explicit set-on/set-off where supported, scoped to a channel when applicable. |
| `PowerMeasurement`, `VoltageMeasurement`, `CurrentMeasurement`, `EnergyMeasurement` | Read-only numeric readings in W, V, A and kWh. Energy declares counter versus interval semantics before use. |
| `TemperatureMeasurement`, `HumidityMeasurement`, `BatteryLevel` | Read-only numeric readings in °C, % relative humidity and % battery level. Battery level is optional and has its own freshness. |
| `Thermostat`, `HeatingSetpoint`, `OperatingMode` | Thermostat groups typed HVAC affordances. Setpoint and mode are independently readable or writable with validated constraints. |
| `FaultStatus`, `ProtectionStatus` | Read-only device-reported states or events, where exposed. Transport failure has its own status. |

Represent support as supported, unsupported or unknown. A supported capability can be read-only, write-only, or read/write. Report device-level capability separately from route availability and current data quality. Enable a write only when its selected binding mapping and the property policy both allow it. Keep declared support stable through sample gaps. Keep unmapped vendor fields unknown until their semantics are confirmed.

## Ingestion and history

Tuya temperature and humidity history uses a dedicated series source for timestamped property reports. Device snapshot time remains available for the live cards. Time-range queries filter by the assigned property and provider binding and cap points per series. Device-view preferences live in migration 006 and store independent order and visibility data per property membership and page.

1. Normalize units, signs, scale and precision at the adapter boundary. Preserve effective precision and mapping version with the series or sample when it can change interpretation. Keep source and sequence where provided, distinguish actual observation time from receipt time, and flag untrusted timestamps or values. Use per-metric expected cadence and freshness. A fresh fetch of an old snapshot does not refresh its age. A sleeping battery sensor can be stale without having reported offline. Failed polls and partial payloads never create synthetic zeros or OFF transitions.
2. Deduplicate provider replay by a stable provider identity scoped to the series, or a unique fingerprint of canonical value, source event time and sequence where available. Advance latest observation quality using source ordering. A newer explicitly invalid observation makes that input unusable for control while keeping the last valid value for display. Persist valid late readings inside the supported lateness window for history without replacing newer current state or generating a new live trigger.
3. Keep state transitions, source or quality changes, and periodic heartbeats. Update current state on genuinely newer observations even if history sampling suppresses repeated values. For numeric gauges use bounded sampling or a metric-specific deadband only when accuracy permits. Preserve counter samples needed for valid deltas. Capture bounded evidence in rule evaluations when the referenced samples may expire sooner than the audit records. Charts mark gaps and partial coverage.
4. Treat W as instantaneous power and kWh as energy. Compute deltas from comparable samples within one validated cumulative counter stream. Use a new baseline after an unknown reset, source change or re-pairing, and correct wraparound only when modulus and continuity are known. Treat a provider-reported interval delta as its own series with an interval identity and coverage. For power-integrated energy use valid intervals with bounded gaps. Preserve gaps and time-weighted coverage in rollups.
5. Compute canonical installation metrics from approved independent components or one authoritative site-wide source. Appliance and nested circuit measurements are a breakdown when the whole-house meter already covers them. Only sum separately commissioned non-overlapping contributors, with comparable intervals, and mark incomplete totals. Persist the boundary version and contributing series. When both cloud and local bindings observe the same meter, choose one canonical stream for each period and keep both as provenance. Never sum them together.

## Retention and migrations

- Milestone 7A enforces no retention. Raw samples and hourly rollups are kept until storage growth is measured. See the [storage estimates](10-historical-telemetry.md#storage). The following defaults remain planning assumptions for a later retention milestone.
- Start with configurable defaults of 30 days of detailed samples and 12 months of hourly rollups. Treat these values as sizing assumptions. Use metric-specific policies for state transitions, audit and faults. At 40 series sampled every minute, the unsuppressed upper bound is about 1.73 million rows per 30 days before indexing. Measure storage, query latency and write volume with representative data before increasing cadence or retention.
- Roll up in small batches using checkpoints and idempotent bucket rebuilds for allowed late data. Finalize buckets before deleting their raw inputs and retain coverage metadata. Index `(observed_at_utc, series_id, sample_id)` for bounded oldest-first purge if measurements justify it. Keep initial tables unpartitioned. MySQL 8.4 partitioned InnoDB tables are incompatible with foreign keys, so revisiting partitioning requires a deliberate schema and workload review. [MySQL partitioning limits](https://dev.mysql.com/doc/refman/8.4/en/partitioning-limitations-storage-engines.html)
- Use immutable numbered SQL scripts under `database/migrations/` and a separate deployment-time runner. Record IDs, checksums and applied times. Run one migration job with a distinct DDL credential. Exercise fresh installation and upgrade in integration tests. Use small, recoverable migrations, an explicit repair/restore path and expand/contract changes where necessary for rollback. Many MySQL DDL statements implicitly commit, so avoid promising atomic rollback across a migration script. [MySQL implicit commits](https://dev.mysql.com/doc/refman/8.4/en/implicit-commit.html)
- Include endpoint identity and the capability catalog in the initial schema design. If the earlier device-level sketch has been implemented by the time this change lands, seed each device's default endpoint, backfill capability and telemetry references while retaining series identity, and switch reads/writes after verification. Add rooms, measurement boundaries and load policy in the phase that uses them. The existing MySQL samples and rollups remain the storage engine for the new metrics.
