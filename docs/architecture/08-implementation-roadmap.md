# Implementation roadmap

Deliver a simulated monitoring slice first. Growatt, Daikin, eWeLink and Tuya work can advance independently once the shared foundation is in place and the relevant access is available. Phase numbers identify work and dependencies. A supported integration can ship as access is verified.

| Phase | Deliverables and dependencies | Acceptance criteria |
| --- | --- | --- |
| 1. Scaffolding and development environment | Add the .NET 10 solution, React/Vite application, Compose development topology and CI from the agreed [structure](02-backend-architecture.md). | A clean checkout builds and runs the backend, frontend and MySQL. CI runs xUnit, Vitest and type checks. Developer startup uses no real provider credentials. |
| 2. Backend, database and React foundation | Apply versioned MySQL migrations. Add Dapper access, identity and property authorization, health, the dashboard shell and API contracts. Depends on 1. | Fresh install and upgrade pass against MySQL 8.4. Users can select an authorized property. API and SignalR deny cross-property access. DB unavailability appears as degraded readiness. |
| 3. Devices and simulated telemetry | Add property and installation inventory, device endpoints and capability metadata, a simulator, ingestion, latest values and a minimal history view. Depends on 2. | Simulate two parallel inverters, a shared battery, an AC and one metering switch or sensor. Show installation totals without double-counting and distinguish stale or missing readings, communication loss and explicit faults. Show simulated health and continued ingestion with the browser closed. |
| 4. Growatt read-only monitoring | Obtain authorized account access, confirm region and SPF fields, map installation metrics and compare with reference readings. Depends on 3 and external access. | Observe both inverter identities and document field coverage, cadence, units, scopes and known gaps. Verify mirrored versus additive data. A simulated or observed communication outage remains distinct from grid loss. If access stays blocked, retain the simulator and capture the supported alternatives. |
| 5. Daikin monitoring and manual control | Register the ONECTA app, discover units, establish a quota budget, and add manual actions through the command ledger. Depends on 3 and the property owner's consent. | Test refresh, throttling and reauthorization with simulated failures. Verify allowed modes, power and setpoints per unit. Show command acceptance separately from readback. A timeout or restart does not automatically reissue a possibly applied command. |
| 6. Historical dashboards and live updates | Add retention, hourly rollups, charts, degraded panels and SignalR invalidation. Depends on 3 and can overlap 4–5. | Display gaps, coverage and source in charts. Recovery after SignalR loss refetches state. Representative-volume ingest and queries meet measured targets, and purging raw inputs preserves finalized rollups. |
| 7. Rules and dry-run | Add the versioned rule catalog, property schedules, overrides, execution history and dry-run replay. Depends on 3 and the shared command contract, which can use the simulator. | Replay normal operation, outage, stable recovery, unknowns and arrival override. Tests cover hysteresis, cooldown, DST, restart and conflicts, and demonstrate zero outbound actions during dry run. |
| 8. Bounded live activation | Commission trusted outage evidence, battery and frost constraints, quota/cadence and approved Daikin action capabilities. Enable one device and one versioned rule and expose critical incident status. Depends on 4 or a verified alternative signal, plus 5 and 7. | Compare dry-run output with observed site behavior first. Supervised trials demonstrate manual priority, safe stale-data handling and restart recovery. Operators can see critical incidents, pause automation and recover manually. |
| 9. Alerts and operational readiness | Add incident views for outage, restoration, low SOC, faults, device offline and automation failure. Add operational dashboards and recovery runbooks. Design notification delivery through the neutral port. | Repeated polls do not reopen the same incident. Operators can see recovery and diagnose stale feeds. Restore an encrypted backup with dispatch paused and meet agreed RPO/RTO. External notification providers are a later choice. |
| 10. eWeLink discovery and monitoring | Register a developer app and add authorized discovery, mapping and read-only ingestion for supported Sonoff/eWeLink models. Depends on 3 and CoolKit access. | Import repeatably without duplicate devices, resolve channels, and show declared and unmapped capabilities. Simulate expired authorization, a missing device and reconnect without disrupting other providers. |
| 11. Tuya discovery and monitoring | Link a Smart Life account to the correct regional project. Add signed API access, discovery and read-only data-point mapping. Depends on 3 and Tuya project access. May run alongside 10. | Show actual device and channel capabilities, including read-only fields and scaled measurements. Exercise rate limiting, expired project access and account unlink independently of other providers. |
| 12. Smart switch commands | Reuse the shared command ledger for explicit on/off with endpoint permissions, eligibility and readback. Start with a supervised non-critical load. Depends on 10 or 11 for the chosen device. | Verify target channel, pending status and readback. Test duplicate requests, provider-side changes, restarts and unknown outcomes. An ambiguous cloud attempt never triggers automatic LAN resend. |
| 13. Room sensors and energy dashboards | Add room grouping, temperature/humidity/battery history, and appliance power and energy views using existing telemetry. Depends on 3 and history from 6. Deliver live mappings as each device is verified. | Show sleeping sensor ages, counter resets and missing intervals. Test eWeLink and Tuya fixtures that render through the same capability panels. Appliance totals remain separate from overlapping whole-house totals. |
| 14. Water heater scheduling and surplus automation | Add a commissioned heater policy, schedule windows, runtime deadlines, and optional verified PV/SOC eligibility. Depends on 7 and 12 for the selected relay plus trusted site measurements and independent hardware protections. | Dry-run minimum times, hysteresis, reserve drops, stale data, manual lockout, unknown ON and overdue OFF. Verify the site-local runtime limit during provider loss and restart before unattended control. Roll out one supervised device with a documented pause and isolation procedure. |
| 15. Optional local agent | Add property-scoped enrollment, read-only discovery/collection, bounded buffering and source reconciliation for an approved local interface. Pilot one verified device and binding. | Observe WAN loss and import buffered data without duplicate history or late live triggers. Confirm alias matching, per-metric source policy and property isolation. The agent has no command authority at this stage. |

## Key technical risks

| Risk | Mitigation and decision gate |
| --- | --- |
| Growatt authorization or SPF coverage is unavailable | Request regional access and a supported contract early. Keep delivery independent with the simulator. Escalate to an approved local read-only source if live coverage is insufficient. |
| Delayed or partial telemetry misidentifies an outage, surplus or household total | Verify observation timestamps, grid evidence and electrical measurement boundaries. Test source disagreement, overlapping counters, self-load feedback and missing samples before activation. |
| Automated load changes conflict with electrical, BMS or temperature constraints | Have the installer reconcile the reported battery and the manufacturer's parallel-installation recommendation. Verify relay and appliance ratings, local runtime limit, physical protections and independent frost protection before unattended control. |
| ONECTA quota, device capabilities or cloud lags limit control | Confirm the actual request model, ranges and readback cadence per unit. Reserve quota for controls and verification. Keep any unsupported action disabled. |
| eWeLink or Tuya has incomplete authorization, model mapping or slow reporting | Verify app/project eligibility, region, plan, channel access, counter scale and report cadence with device fixtures. Start with separate read-only integrations. |
| Multiple routes, retries or restarts repeat or obscure equipment commands | Confirm physical identity before linking. Persist intent, route and attempt before dispatch, arbitrate per device, and reconcile uncertainty. Test duplicate push events, competing routes, vendor schedules and restored queues. |

## Open decisions and validation owners

| Question | Decision owner and timing |
| --- | --- |
| Which Growatt region, data logger, firmware and approved API path apply? Which metrics are per device, shared or site totals? | Owner/installer with Growatt support, before 4. |
| Which Daikin models and ONECTA entitlements apply? Can each target unit heat at 10 °C and report verified state within the quota? | Owner/developer with Daikin portal access, before 5 and 8. |
| Which eWeLink/Sonoff and Smart Life models, firmware, output channels, sensor fields and report cadences are installed? What CoolKit app approval, Tuya data center and service plan apply? | Owner/developer, before 10–12. |
| What grid signal and maximum tolerated age can support live control? What are the BMS load envelope, SOC hysteresis, frost floor, occupancy definition and override lifetime? | Owner and installer, before 8. |
| What appliance and circuit ratings, independent cutoff, approved operating window and fallback apply to the heater? Which measurements cover the whole house or only a subset, and how will surplus be verified? | Owner and installer, before 14. |
| Which initial deployment location, remote access model, host power backup, property timezone and RPO/RTO should be used? | Owner/operator, select during 1 and confirm before live use. |
| How much ingest cadence and history retention is useful? Which supported gateway, MQTT or Matter paths are available and what benefit justifies an agent? | Owner/developer using pilot measurements, during 6 and before 15. |

## Recommended first milestone

Bundle phases 1–3 into a simulated monitoring slice. Launch the Compose stack, authenticate, and use the React dashboard to display current values and short history from MySQL. Seed a parallel solar installation, a Daikin unit and a simple simulated meter or sensor. Demonstrate health, a telemetry gap, a fault, and ingestion with the browser closed. Include migration, property authorization, normalization and freshness tests. Run provider research separately so the milestone can ship with simulated data and standard Compose services.
