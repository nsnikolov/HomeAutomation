# Backend architecture

## Solution boundaries

Use one .NET 10 ASP.NET Core Web API process. Four initial production projects separate domain behavior, use cases, infrastructure, and hosting. Growatt, Daikin, eWeLink, Tuya and simulator adapters have separate Infrastructure namespaces. Extract an adapter into its own project if dependencies, ownership, or reuse justify it. See [ADR 0001](adr/0001-modular-monolith.md).

```text
├── HomeAutomation.slnx
├── src/
│   ├── backend/
│   │   ├── HomeAutomation.Api/

│   │   ├── HomeAutomation.Domain/

├── docs/architecture/
└── docker/
```

## Modules

- **Properties and devices** own memberships, rooms, installations, inventory, capabilities, integration connections and external identities. Device type and manufacturer help classify inventory. Capabilities drive actions and views. Admins own mapping and confirmation, including when an existing device gains a second provider binding.
- **Telemetry** owns normalization, provenance, source selection, current reported state, history and rollups. Connectivity tracks last successful target communication separately from the provider account's last successful poll. Missing a target in a list response is insufficient to mark a fault. Persist faults only when reported by the device/provider or identified by an explicit fault signal.
- **Automation and control** own rule versions, schedules, overrides, desired state, evaluation history, command arbitration, dispatch and reconciliation. Manual and automated writes enter the same device command path. The frontend and pollers cannot call a provider's write adapter directly.
- **Alerts** own incident identity, opening, recovery and deduplication. A transactional incident record links safe evidence to the triggering observation or execution. A future delivery worker uses a provider-neutral notification port with persisted per-channel delivery status and deduplication.

Modules share a database. Each module owns its write paths and exposes use cases or narrow read models to other modules. Use transactions across modules where one invariant requires it, such as recording a rule outcome and enqueuing its command. Avoid generic repositories or an event bus until there is a concrete consumer need.

## Hosted workers

| Worker | Behavior |
| --- | --- |
| Provider ingestion | One in-flight poll per connection, with bounded concurrency across connections, provider-aware pacing and jitter. Supervise permitted push subscriptions independently with bounded reconnect and catch-up reads. Polls and events use the same versioned normalization and idempotent ingestion path. Coalesce refresh requests and track contact, sample time and failure independently. |
| Automation evaluation | Drain durable work generated by accepted relevant observations and due schedules. Serialize evaluations by property, use deterministic rule ordering and store checkpoint, decisions and resulting intents transactionally. Wake on a local signal for speed and scan MySQL for recovery. |
| Command dispatch and verification | Claim committed intents and serialize external writes per physical device across channels and providers. Recheck policy and select one authorized write binding before sending. Record the binding and reconcile ambiguous outcomes before considering a different route. Independent devices progress within account and site load budgets. See the [execution model](06-automation-engine.md). |
| History and alert maintenance | Advance rollups and retention in bounded batches. Evaluate freshness and incident transitions on time as well as data changes. Process alert delivery separately when a transport is added. |

Create a DI scope per worker unit of work, await owned tasks and propagate cancellation to reads and delays. Stop taking new work during shutdown and allow bounded time to persist send outcomes. An interrupted send remains eligible for reconciliation on startup. A provider error backs off its own connection. Fatal configuration errors fail startup for essential enabled features, while an unconfigured optional provider remains disabled. Deploy one active host with stop-first replacement. Additional active hosts require explicit ownership for polling, evaluation and dispatch before scaling. [Microsoft hosted services guidance](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/host/hosted-services?view=aspnetcore-10.0)

## Integration and transport boundaries

Application-owned ports cover discovery, snapshot reads, optional observation subscriptions, and optional command sending and verification. Each adapter owns provider DTOs, auth, cadence and feature mapping. Only enable writes on an explicitly supported binding and target. Application use cases own device inventory, authorization, binding selection and command policy. See [integration contracts](05-integrations.md) and [ADR 0007](adr/0007-device-capabilities-and-provider-bindings.md).

### Discovery and configuration

1. An admin opens a connection for a property through the provider-specific onboarding flow. Store a credential reference and expose safe connection status such as connected, authorization required, throttled or disabled.
2. List discovery candidates with model, channels, availability and mapped/unmapped capabilities. Providers without discovery can use a manually configured external identity or an agent-enrolled device. Validate it through the adapter before allowing control. Pairing can still require the vendor app or hub.
3. Import as a new device or explicitly attach to an existing physical record. Verify a trusted shared identifier or compare device labels, channel mapping and site evidence. Offer a review when identity is uncertain. Assign the property, optional room and friendly name. Use property-scoped uniqueness and idempotent import to handle repeated discovery.
4. Enable monitoring independently. Remote control starts disabled and is enabled per permitted target after verification and policy checks. Show last discovery sync, last successful communication per binding, online/offline/unknown state, and age per measurement. A missing discovery result calls for investigation, with no automatic deletion or reassignment. If mappings or capability access change, invalidate affected queued writes and revalidate before resuming.

### API and live updates

- **REST.** Group routes under `/api/v1/properties/{propertyId}` for rooms, devices, discovery, integrations, state, history, rules, overrides, command status and alerts. Accept typed targets by application device and channel identity. Use bounded ranges and cursor pagination. Return a command ID and status URL with `202 Accepted` for queued control. Property-scoped idempotency keys match the actor, operation and payload fingerprint. Reusing a key with a different payload yields `409`. Use `ProblemDetails` with stable error codes and correlation IDs.
- **SignalR.** Authenticate subscriptions and check property membership on the server. Push compact post-commit state invalidations with property and entity identifiers and state revisions where available. Treat pushes as hints. Fetch through REST on initial load and reconnect, and use a modest fallback refresh while disconnected. Applications and workers run without SignalR clients.
- **Testing.** Use xUnit for domain behavior and timing with a fake `TimeProvider`. Exercise actual MySQL migrations, transaction and claim behavior in isolated integration tests, plus ASP.NET Core authorization and API contracts. Simulate provider errors and write/readback behavior. See the [roadmap](08-implementation-roadmap.md) for phase gates.
